### 1. 范围与接入

**需求**:
- iron-m 以 mirobody 官方的 Agent 插件方式接入，替换 mirobody 自带的 Agent；mirobody 的登录、对话记录、流式输出、网页照常使用。
- 第一版只做问答：用户在 mirobody 网页的对话里提问，由 iron-m 的多 Agent 作答。

**约束**:
- 不修改 mirobody 源码，只通过它公开的插件接口、数据查询接口和对话记录接口工作。
- 只能读当前这个人的健康数据（mirobody 已经判定过的那个人），不能跨人读。

**非目标**（第一版）: 当日计划、训练记录、档案、提醒推送、分节显示的专用前端、白名单登录、mirobody 底座问题的修补。

### 2. Agent 组成

**需求**: 第一版有 7 个 Agent，各自的职责、能用的工具和资料如下。

| Agent | 负责什么 | 能用什么 |
|---|---|---|
| 主教练 | 理解问题、决定请哪些专业 Agent、整合成一个回答；直接回答闲聊、App 用法 | 本会话最近几轮对话 |
| 训练规划 | 训练频率、组数次数、强度、有氧与力量的安排 | 依据库（训练） |
| 动作教练 | 动作做法与要点、常见错误、替代动作 | 依据库（动作） |
| 营养 | 饮食原则、蛋白质、补剂、减脂饮食 | 依据库（营养） |
| 恢复 | 睡眠、疲劳、酸痛、恢复相关的身体指标 | 健康数据、依据库（恢复） |
| 数据分析 | 体重、心率、步数、血压等的趋势与解读 | 健康数据 |
| 安全官 | 每次都参与：风险、身体不适、特殊人群、什么时候该就医 | 依据库（安全） |

**约束**:
- 每个专业 Agent 只能用表中列出的工具和资料。
- 同一轮里各专业 Agent 看不到彼此的意见。

### 3. 一轮回答的流程

**需求**:

1. **安全前置**：只用规则，不调用模型。
   - **急症或红旗**：要区分说的是本人还是旁人，要识别否定说法（如"没有胸痛"）和过去发生过的事。命中时直接给固定的四段式回答：安全结论、立即停止的事、不能判断的部分、该找的专业帮助。这一轮到此结束。
   - **拒答**（诊断、开药、治疗方案、代叫急救）：先给固定的说明，再照常回答其中可以讨论的部分（如什么情况要就医、能怎么活动）。
2. **理解与调度**：由主教练完成，调用 1 次模型。
   - 判断这句话属于闲聊、App 用法、专业问题还是超出范围。
   - 判断是否涉及身体不适或特殊人群。
   - 选出 1 个主责 Agent，加最多 2 个辅助 Agent，并说明理由。
   - 调度结果要过规则校验：
     - 只能从名单里选；
     - 主责 1 个、辅助最多 2 个；
     - 安全官必须参加；
     - 涉及恢复和训练时，恢复先于训练；
     - 提到身体不适或特殊人群的，一律按专业问题处理。
   - 校验不通过或模型不可用时，改按问题里的关键词打分来选，并在运行记录里写明。
   - 闲聊和 App 用法由主教练直接回答，不给具体的训练量、热量、剂量数字。
3. **专业 Agent 同时作答**：
   - 每个 Agent 先查自己能查的东西：健康数据，或者本领域的依据库。可以连续查询，每轮最多 3 次。
   - 然后写出固定格式的意见：结论、针对你、怎么做、注意、不确定的地方。每句话写的时候就标好出处：用到资料的句子在句末标资料编号，用到健康数据的句子写成网页可以点开的引用格式。意见按第 5 步同样的规则逐句核对，不合格改一次，仍不合格就不发言。
   - 查不到能回答这个问题的依据时，这个 Agent 不发言，并写明原因。
4. **整合**：由主教练完成，调用 1 次模型。
   - 主责的意见放在前面。
   - 安全官的提醒不交给模型改写，由系统原样放在回答最后的"安全提醒"里；其他内容不能与它矛盾。
   - 只使用各专业 Agent 给出的内容和依据，不新增事实。
   - 回答按统一结构写：结论 → 针对你 → 怎么做 → 注意 → 依据。简单问题可以只有结论和依据。
5. **审核**：只用规则。
   - 检查项：
     - 逐句核对：每句话里的数字，都能在这一句标注的出处里找到（这一句引用的资料或数据行），或者是用户自己说的；没标出处的句子不能有数字；
     - 引用的编号都真实存在；
   - 不通过时，带着原因让模型改写 1 次。
   - 仍不通过时降级：把各专业 Agent 的意见逐段列出，或者回答"这次没能给出可靠的回答"，并告诉用户这次回答受限。

**需求**（展示）:
- 每个参与的 Agent 在网页上显示为一个可以展开的条目，内容包括：
  - 角色名；
  - 结果：写出了意见，或者没有发言及原因；
  - 查了哪些数据。
- 引用健康数据的依据可以点开，看到是哪条数据、什么时间。
- 降级时显示提示。

### 4. 健康数据

**需求**:
- 恢复、数据分析两个 Agent 可以查询这个人在 mirobody 里的健康数据，包括读数、趋势、统计、最新值。每行数据都带 mirobody 的引用编号。
- 回答引用健康数据时，使用 mirobody 能识别的引用格式，网页上可以点开。
- 没有记录时如实说明，例如"没有找到你的睡眠记录"，不能推断为正常，也不能编数字。
- 苹果手表记录的心率变异性（SDNN）与其他设备记录的（RMSSD）算法不同，分开说明，不放在一起比较。

### 5. 依据库

**需求**:
- 自建依据库，首批约 20 条，只用公开可得的资料。覆盖：
  - 身体活动总量：世界卫生组织 2020 年指南、《中国人群身体活动指南（2021）》；
  - 力量训练的基本原则、有氧强度；
  - 热身与恢复、睡眠；
  - 蛋白质、肌酸、咖啡因；
  - 补水与热环境；
  - 疼痛与就医指征、运动前筛查。
- 每条包括：来源名称、发布机构、年份、证据等级、适用人群、用自己的话写的摘要、可以核对的要点（注明在原文中的位置）、审定状态。
- 由 Claude 对照原文审定并留下记录。未审定的条目不参与回答。（我的判断，待确认）
- **证据等级**从高到低：指南与立场声明 > 系统综述 > 随机对照研究 > 其他研究 > 专家意见。

**约束**: 有版权的原文不进仓库，回答中的摘录不超过 80 字。

### 6. 安全

**需求**:
- 急症、红旗、拒答都写在规则和词表里，不依赖提示词。命中时用固定回答，不调用模型。
- 急症词表、拒答词表和固定回答的内容，沿用 IronM 已审定的版本：只用这些内容数据，不用 IronM 的代码。（我的判断，待确认）
- 涉及疼痛的回答，都要写明出现什么情况必须停止并就医。

### 7. 对话记忆

**需求**:
- 每轮读取本会话最近 6 轮对话，只用来理解指代，例如"那个动作""上面说的"。
- 用户在对话中提到的个人信息不自动写入档案。

### 8. 模型

**需求**:
- 调度、作答、整合三个环节可以分别配置模型。默认都用 DeepSeek 的 deepseek-flash，不开思考。
- 每次调用 30 秒超时，最多重试 1 次。
- 每轮的模型调用总数有上限（默认 16 次）。超过上限时停止查询，用已有的结果作答。
- 密钥只从环境变量读取，不写进配置、日志和回答。

### 9. 运行记录与日志

**需求**:
- 每轮记录以下内容：参与的 Agent 和各自的结果、调度方式（模型还是关键词）、工具调用次数、依据编号、模型调用次数与耗时、是否降级和原因。
- 运行记录和日志都不含用户原话、回答原文和健康数据的数值。

### 10. 考题与验收（先出题、再实现）

**需求**:
- 动手实现前先出首批考题 50 道。每道题写明必须满足什么、不能出现什么：
  - 安全 15 道：急症、旁人急症、否定说法、既往、四类拒答；
  - 健康数据 10 道：有数据、没有数据、两种心率变异性；
  - 知识 15 道：训练、动作、营养、恢复；
  - 闲聊与 App 用法 5 道；
  - 多领域 5 道。
- 判分方式：
  - 安全题只用规则判；
  - 其他题用规则检查加模型评委。评委用和作答不同的模型（我的判断：Kimi，待确认）。
- 第一版的门槛：
  - 安全题 100% 通过；
  - 编造的出处为 0；
  - 回答里的数字 100% 可以追溯；
  - 没有依据的题如实说明的比例 ≥ 90%；
  - 健康数据题的引用都能点开。
- 单元测试不调用真实的模型和数据库；用真实模型的评测单独运行。

### 11. 功能页面（第一轮）

**需求**:
- 自建网页，和 mirobody 同一个地址、同一套登录；底部导航：首页、动作、饮食、数据；右上角"我的"。每页都能跳到对话提问。
- 第一轮做：页面框架、"我的"档案、数据页（全部可计算的指标）、首页的今日概况与今日营养目标、饮食页的今日目标。动作库、训练记录、拍照算热量、今日训练计划放到后续几轮。（我的判断，待确认）
- 手机宽度优先，跟随系统深浅色。

**约束**: 不修改 mirobody 源码；页面只调用 mirobody 与 iron-m 的接口。

### 12. 指标计算

**需求**:
- "我的"档案：身高、出生日期、性别、目标（增肌、力量、减脂、耐力、综合健康）、日常活动水平。mirobody 里已有的（性别、出生日期、身高读数）自动带出，用户可以改。
- 由 iron-m 计算、每个数都说明怎么算、用了哪些数据、依据哪份资料；数据不够时说明还缺什么，不给出数字：
  - 体重：最新值、近 7 天平均、近 4 周每周变化（带可信范围）；
  - BMI 与中国成年人分类；
  - 基础代谢、每日总消耗、按目标的每日热量与蛋白质目标；
  - 静息心率、心率变异性：近 7 天平均与本人近 60 天基线的比较（不同算法的心率变异性分开）；
  - 睡眠：近 7 天平均时长，与每晚 7 小时的建议比较；
  - 步数：近 7 天平均，与每天 8000–10000 步的参考比较；
  - 血压：最近一次与分级（只作参考，不作诊断）。
- 问答中，营养、数据分析、恢复、训练规划可以调用同一份计算，回答里的这些数字可以追溯到计算过程。

**约束**: 计算用的公式与参数写明出处；健康数据只在本人的请求里计算，不写入日志。

### 13. 去掉安全官；被请到的 Agent 必须回答（项目负责人决定）

**Supersedes**: 本日 §2 表中"安全官"一行与"安全官每次都参与"；§3 第 3 步"查不到依据时这个 Agent 不发言"、第 4 步"安全官的提醒必须保留"、第 5 步"仍不通过时降级"；§5"未审定的条目不参与回答"中"查不到就不回答"的做法。

**需求**:
- 不再有安全官这个 Agent。风险与就医提醒由各专业 Agent 在自己的回答里说明（原来只有安全官能查的"运动前筛查、受伤就医、热环境、孕期、生病"资料分给训练规划、动作教练、营养、恢复）。
- 急症与拒答的规则拦截（不是 Agent，不调用模型）保留：命中急症仍直接给固定的急救指引。
- 被主教练请到的专业 Agent 一定要从自己的专业角度回答这个问题：
  - 依据库或用户数据里查到的，照常标出处；
  - 查不到的，用专业经验回答，这些句子标〔经验〕，回答末尾说明〔经验〕的含义。
- 核对不再让 Agent 整条不发言：改一次还不过时，引用个人数据却对不上的句子删掉（不能把人的数据说错），其余对不上出处的句子改标〔经验〕。
- 主教练整合时不能自己加数字：经验句里的数字必须出自某位专业 Agent 的意见，否则删掉这句。
- 回答只用和这次问题直接相关的个人数据与计算结果。

### 14. 回答精炼；来源按需解释（项目负责人决定）

**Supersedes**: 本日 §3 中"回答按统一结构写：结论 → 针对你 → 怎么做 → 注意 → 依据"与"引用健康数据的依据可以点开"作为正文的一部分；§13 中"回答末尾说明〔经验〕的含义"。

**需求**:
- 回答正文只讲结论和做法，有效、精炼：简单问题不超过约 150 字，需要分步骤的不超过约 300 字、最多 5 个要点；不写出处标记、不列参考资料、不用小标题。
- 只用真正改变建议的个人数据（比如按体重算剂量），不为显得个人化而提体重等数据。
- 可溯源性不变，但不放在正文里：后台照常逐句核对出处；每条回答下面附一个可展开的"依据与来源"，列出用到的个人数据（指标、日期）、计算过程、资料，以及哪些部分是教练经验。
- 用户追问来源（"这个数从哪来的""依据是什么""2764 是怎么算的"）时，直接用上一条回答的"依据与来源"解释；问到具体数字时只讲这个数字是怎么来的；连续追问时跳过上一次的追问回复，指向真正的回答。不再请专业 Agent，不调用模型。

### 15. Agent 记忆（参考 TencentDB Agent Memory 的分层，自己实现）

背景：试跑腾讯的记忆引擎，提取快、分层好，但在健身场景漏记器械、情况变化不更新、画像会推测编造、关键词召回查不全；技能沉淀产出为 0。项目负责人决定照它的思路自己实现。

**需求**（分层）:
- **L0 原始对话**：用 mirobody 已存的对话记录，不另存。
- **L1 记忆条目**：每轮问答结束后在后台提取，按类别记：伤病与身体状况、器械与场地、可练时间、饮食限制与习惯、喜好与讨厌、目标、回答风格、近期事件、给过的关键建议。每条有状态（有效 / 已解决 / 被新说法取代），情况变化时更新原来那条，不重复新增。
- **L2 分领域记忆**：按类别分给各专业 Agent：训练规划读器械、时间、伤病、目标、近期事件；动作教练读伤病、器械；营养读饮食、目标；恢复读伤病、近期事件、作息；数据分析读目标；所有人读喜好、回答风格和最近几条给过的建议（保持前后一致）。
- **L3 画像**：由有效的记忆条目直接整理成简短的条目清单，不经模型改写，所以不会出现用户没说过的推测。主教练调度与整合时使用。
- **会话内的短期记忆**：同一会话里，除了用户前几句话，也带上前几轮回答的要点，便于理解"上面说的"。

**需求**（写入规则）:
- 每条记忆必须附上用户原话里的片段（"给过的建议"附回答里的片段），片段在原文里找不到就不记，防止编造。
- 用户明确说的事实直接生效；系统推断的放"待确认"，用户确认前不用于回答。
- 作答前把这个人全部有效记忆读进来（一个人通常几十条），不靠关键词检索，避免漏召回。
- 提取在后台进行，不拖慢回答；提取失败不影响回答。
- 记忆里的数字只能出自原话（更新时也可以出自被更新的那条），防止把数字记错。
- "给过的建议"每轮最多记 1 条：只记针对这个人做出的最关键的决定（换了什么动作、避开什么、计划怎么定）；一般的训练原则（组数次数、休息、加重规则、热身放松、就医提醒）不记。
- 近期事件 14 天后不再用于回答（"我的记忆"里显示为已过期）。

### 16. 前端合一、页面重做（项目负责人：前端页面不要分成两部分，每个页面都很潦草）

**需求**:
- 只有一个前端：对话（问教练）做进同一个网页，作为底部导航的一项；所有"问教练"入口都在本页打开对话，不再跳到 mirobody 自带的网页。对话里能看到各角色的进度、回答、可展开的"依据与来源"，每条回答可以评"有用 / 没用"（存为 1 / −1，以后提炼技能用）。重新打开时接着显示最近一次对话。
- 每个页面重做：一张卡片只放一个数和一个短结论（如"正常""基本持平"），长说明、怎么算的、用了哪些数据放进点开后的详情；不放"下一轮上线"之类的占位卡片；数据过期的提示弱化成一行小字；没有数据时给出简洁的空状态。
- 首页：今天的身体状态（静息心率、心率变异性、睡眠对本人基线的结论，合成一句话）、今日营养目标、"让教练安排今天的训练"（在对话里生成）。
- 动作：动作库，按部位、器械筛选；每个动作写做法、要点、常见错误、更容易 / 更难的替代、什么情况先别做；每个动作可以直接问动作教练。
- 饮食：今日热量与蛋白质目标、每餐蛋白质怎么分、能量估算（基础代谢、每日总消耗），常见问题一键问营养师。

- 我的：档案（身高、出生日期、性别、目标、活动水平）与退出登录。

### 17. 数据上传与导入；不要关爱圈（项目负责人：mirobody 的一些上传功能在首页没了，还有一些数据导入，关爱圈可以不要）

背景：mirobody 自带网页的"数据"页有记录、文件、基因数据、连接数据源四项，前端合一（§16）后这些入口没有了。

**需求**:
- 首页和数据页都有"添加数据"入口：上传报告、随手记一条、导入苹果健康、基因数据、连接设备。
- 上传报告：体检报告、化验单等（PDF、图片、Excel/CSV、Word、文本），单个不超过 20MB，可以一次选多个，显示上传进度；上传后自动识别其中的指标。数据页列出已上传的文件：上传时间、报告日期、识别状态与识别出的项数；可以查看原文件、修改报告日期、删除（从它识别出的数据一并去掉）。
- 随手记一条：用自己的话写（如"今天头疼，血压 130/85"），一句话里写几件也行；记下后显示记成了什么，没记的说明原因；能看到最近 30 天的记录，可以删除单条。
- 导入苹果健康：上传 iPhone"健康"App 导出的压缩包，在后台导入，页面显示进度和结果（读到多少条、新增多少条）；同一个文件再导入不会重复计数；导入后睡眠、心率变异性、步数等指标随之更新。
- 基因数据：上传消费级基因检测的原始数据文件（WeGene、23andMe、AncestryDNA、VCF 等），显示当前生效的集合概况，不展示具体基因型。
- 连接设备：列出服务端已配置的设备数据源（Garmin、Oura、Whoop）和连接状态，可以连接、断开；一个都没配置时说明原因，引导用上传或导入。
- 数据页新增"全部指标"：所有指标（含从报告里识别出的化验值）的最新值、单位、记录数和最近日期，常见指标显示中文名。
- 不要关爱圈：网页上不提供关爱圈；有人从其他入口替别人提问时，教练只说明不支持，不读写对方的数据和记忆。

**约束**: 上传和导入的数据只进当前登录的人自己的记录；查看原文件需要登录凭证；不加载外部资源。

**非目标**: 拍照算热量另议；设备连接需要各家厂商的开发者凭证和公网回调地址，本机无法实测。
